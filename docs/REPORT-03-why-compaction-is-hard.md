# 压缩对话：为什么它不像听起来那么简单

> 写给觉得"不就是超了把旧消息总结一下吗"的人。
> 这份文档不讲代码，只讲**每一环为什么必须这么做**，以及不做会出什么事。

---

## 表面看上去是这样

```
对话太长了 → 把前面的总结成一段 → 继续聊
```

三行说得完。

## 实际是这样

```
触发判断 → 抢先备份 → 增量计算 → 会话隔离 → 摘要生成 → 上下文重排
   ↓           ↓           ↓           ↓           ↓           ↓
 多处并发    失败不能    重复存储    跨会话    摘要失败    摘要自己
 要加锁      拖垮主流程  会撑爆磁盘    泄露      要说清楚    也要被压
                                                    ↓
                                              事后检索
                                        强制问用户 / 限长度 / 限条数
                                        目录要能精确清理
```

下面一条条说。

---

## 难点一：什么时候压，比怎么压更难

**看起来**：算一下 token，超了就压。

**实际上**，这段逻辑跑在每一步工具调用之间。一轮对话里模型可能调十几次工具，每次回到循环开头都会重新算一次 token。

于是会出现：

- 同一次压缩被触发好几次（并发重入）
- 压到一半用户点停止，状态卡在"压缩中"
- 压缩过程中又进来一条新消息，边界算错

**所以必须**：给每个会话一把锁，压缩期间其他触发直接跳过；并且"没有新消息可压"时要优雅返回，而不是报错。

这一环不加锁的后果不是"慢一点"，是**同一份存档被写两遍、上下文被压两次、摘要叠摘要**，最后对话内容直接乱掉。

---

## 难点二：摘要会丢东西，所以必须先备份

**看起来**：总结一下就行。

**实际上**，摘要是有损的。丢了什么？通常正是最需要的那些：

- 具体的文件路径
- 执行过的命令
- 工具返回的原始结果
- 用户当时的原话

模型压缩完，你问它"刚才那个路径是什么"，它只能含糊其辞。

**所以必须**：**在调用摘要模型之前**，先把完整原文存一份。顺序不能反——先摘要后备份，一旦摘要失败，原文就没了。

而且这段备份**不能影响主流程**：磁盘满了、路径没权限、文件锁了，都只记一条日志，压缩照常进行。摘要才是主干，备份是保险。

---

## 难点三：每次都存全量，等于没设计

**看起来**：每次压缩前存一份完整对话，简单。

**实际上**：

```
第一次压缩：存 1、2
第二次压缩：又存 1、2、3      ← 1、2 已经存过了
第三次压缩：又存 1、2、3、4   ← 重复得越来越多
```

十几次压缩之后，磁盘上全是重复内容，而且用户翻存档时会看到同一段对话出现好几遍。

**所以必须**：只存**增量**。

实现上要记一个"上次存到哪条消息"的记号，每次只取它之后的部分。而且这个记号要能扛住：

- 用户编辑了历史消息
- 删除中间某条
- 会话被分支

—— 这也是为什么用**消息时间戳**而不是"第几条"。

---

## 难点四：会话之间必须硬隔离

**看起来**：按房间存就行。

**实际上**，最初的设计是 `助手名/会话名/`。两个坑：

**坑一，重名**。两个会话都叫「新对话」，存档直接搅在一起。

**坑二，更严重**——检索工具如果不限定当前会话，**A 会话的模型能看到 B 会话的全部历史**。这不是 bug，是数据泄露。

**所以必须**：

1. 目录名带上唯一标识（名字给人看，标识保证不撞）
2. 检索工具从调用上下文里拿当前会话，**强制限定**，模型根本拿不到别人的存档

第二条是关键：**不能靠提示词约束**（"请不要查看其他会话"），要靠代码层直接不给。

---

## 难点五：检索本身就是个炸弹

**看起来**：存了文件，让模型搜一下关键词就完了。

**实际上**，这里有个反直觉的陷阱：

> 压缩的**目的**是腾出上下文空间；
> 但如果检索时把整篇存档读回来，**等于把腾出来的空间又塞满**。

一份存档几万字，读三份就直接爆掉，触发又一次压缩，然后又要检索……死循环。

**所以必须**三道闸：

1. **优先搜关键词**，不整篇读——工具描述里写死"prefer search over read"
2. **读也截断**，超过一万多字就砍，并附带一句"下次优先用搜索"
3. **每次最多十几条命中、每条两百字**，把回复体积压住

还有一道更硬的闸：**检索必须指定"查哪一份"**。

```
不带序号直接搜 → 工具直接拒绝
返回一句话：先用 list 列出存档，然后问用户要查哪一份
```

为什么这么设计？因为模型很"勤快"——你让它查历史，它会把所有存档全读一遍。必须靠工具层拦住，光在提示词里说"要先问用户"是没用的。

---

## 难点六：清理要跟着生命周期走

**看起来**：删了就删了。

**实际上**，存档在 App 私有目录，**不在数据库里**。删会话、删助手时，数据库级联删除不会碰它。

结果就是：会话删光了，存档目录里还躺着一堆没人认领的文件，越积越多。

**所以必须**两处挂钩：

| 操作 | 要清什么 |
|---|---|
| 删会话 | 精确删这个会话的目录（靠唯一标识匹配，不能靠名字） |
| 删助手 | 删整个助手目录 |

而且清理失败不能抛异常——删会话是主流程，存档清不掉最多留个垃圾文件，不能因此让删除失败。

---

## 难点七：两个数字长得像，其实是两回事

**看起来**：一个"大小"就够了。

**实际上**，压缩涉及两个完全不同的指标：

| 指标 | 含义 | 用错会怎样 |
|---|---|---|
| **压缩阈值** | 超过多少**才开始压** | 填成目标大小 → 永远压不动 / 频繁触发 |
| **压缩大小** | 压完缩到多少 | 填成阈值 → 压完还是超，下一轮立刻又压 |

这两个必须分开配。第一次实现时把它俩合成一个输入框，用户填完发现行为完全不对。

---

## 难点八：输入框也能咬人

**看起来**：数字输入框，`toInt()` 就完了。

**实际上**，如果输入框的值每次都从配置里读、每次按键都写回配置：

```
用户删掉 "0" → 输入框空 → 解析成 null → 兜底写回 0 → 输入框又变 "0"
                                              ↑
                                    光标重置，用户再打一位 → "05" → 5
                                              再打 → 50
```

用户明明只想填 5，结果变成 50。

**所以必须**：输入框自己维护一份临时状态，空就让它空着，只有解析出合法数字才写回配置。

---

## 完整链路（一次压缩发生了什么）

```
① 每步工具循环结束，检查上下文用量
        ↓
② 超过阈值？并且没有正在进行的压缩？
        ↓ 是
③ 抢锁，进入压缩
        ↓
④ 【备份】把"待压缩的这批消息"写成文件
        ├─ 只写上次之后新增的（增量）
        ├─ 目录带唯一标识（不串会话）
        └─ 失败只记日志，不中断
        ↓
⑤ 【摘要】调用压缩模型
        ├─ 明确告诉它保留什么（文件路径/命令/结论）
        ├─ 用户还能追加自己的要求
        └─ 失败则放弃本次压缩，原文不动
        ↓
⑥ 【重排】摘要 + 最近 N 条原文 → 新的上下文
        ↓
⑦ 释放锁，继续对话

事后：
⑧ 模型想不起细节 → 调检索
        ├─ 先列出这个会话有哪些存档
        ├─ 问用户要查哪一份（工具层强制）
        ├─ 只搜关键词，不整篇读
        └─ 命中条数和每条长度都有上限
```

---

## 每一环的失败模式

| 环节 | 不做会怎样 |
|---|---|
| 不加锁 | 同一次压缩被触发多次，摘要叠摘要 |
| 不先备份 | 摘要失败后原文永久丢失 |
| 备份不分增量 | 磁盘里全是重复内容 |
| 目录不带唯一标识 | 同名会话的存档混在一起 |
| 检索不限定会话 | **别的会话的模型能读到你的历史** |
| 检索不限长度 | 读回来就把上下文撑爆，触发新一轮压缩 |
| 只靠提示词约束 | 模型不听话，全量翻一遍存档 |
| 不挂钩清理 | 删光会话后存档目录仍在膨胀 |
| 阈值和大小混用 | 压缩行为完全不对 |
| 输入框直接绑定配置 | 填 5 变成 50 |

---

## 一句话总结

**"压缩"这个词听起来是一个动作，实际是八个环节串起来的一条链，每个环节都有自己的失败模式。**

能做到"能跑"只需要两三个环节；要做到"跑得稳、不出事、还能查回来"，八个环节一个都不能少。
